# P1-01：网页修复运行与人工审批

2026-10-16。Feature P1。状态：planned → ready → in_progress；B1a内部接收账本、B1b执行与恢复、B2 API、B3页面操作已验收，B4人工决定与精确补丁下载进入 in_review。前置为P0-06与UI-08验收完成；范围保持本地可信单用户、两个固定审核案例和现有模型。

## 1. 用户操作闭环

在现有「修复」页选择案例与单/三角色模式 → 查看固定预算 → 开始 → 看到真实阶段与用量 → 必要时停止 → 审阅候选diff与四格回归 → 明确接受或拒绝候选 → 下载所选补丁。刷新、断网和历史记录均可返回同一任务。

“候选验证通过”“人工已接受”“补丁已写回”必须分开。此项人工接受只记录对确定版本候选的审阅决定，提供显式补丁下载；不写回任意用户仓库。用户实际应用补丁仍需自行操作。若后续加入写回，必须先具备用户选定目标、原始版本检查与冲突/回滚规格，不能借接受按钮隐式写入。

B3已接通修复页开始/停止，交付验收见[39](39-p1-01-b3-web-controls.md)；B4实现见[40](40-p1-01-b4-approval-download.md)。CLI、原报告、历史未知状态保持可读取。

## 3. 接收与执行权

- 请求建议为严格 `{request_id, case_id, mode}`，案例仅 `output_mismatch` / `counter_offset`，模式仅 `single_role` / `three_role`。拒绝模型名、端点、源码、路径、命令、任意预算或验收集字段。
- 固定预算复用P0-06：最多12模型请求、20工具、2候选、600秒、总计2,000,000 tokens、单次8192输出；前置模型配置、镜像与版本校验失败不启动。
- 接收表与RepairTask初始状态在同一SQLite事务落盘；同ID同参只返回原任务，异参409，清理后墓碑410。提交成功后才能202。响应丢失不能生成第二个任务。
- 复用已经验证的owner/task fence和一次性claim思路，不复制另一套预算控制器。仅首次接收方获取claim；事务原子消费claim与推进初始状态；CLI原路径必须继续通过原回归。
- repair网页执行槽单独最多1项；不得以UI按钮禁用代替服务端约束。与现有复现/分析槽的并行资源上限须在B1预审明确写出；未知/待回收资源不释放槽。
- 锁序固定为repair网页owner→task fence→短事务。停止只写持久取消请求，不等待owner长锁。HTTP断开不取消已接收执行。
- 进程暂停仍持owner；死亡后禁止旧claim继续执行。恢复沿用只读inspect与显式清理/对账，不自动重发模型或工具请求。
- 所有新增表采用显式additive迁移；验收使用独立库。用户主库升级需停写、备份及逐表保真核验；不得随API启动自动迁移。

## 4. API与页面契约

拟新增 `/api/repair-runs/catalog`、`POST /api/repair-runs`、`POST /api/repair-runs/{id}/cancel`，复用现有 `/api/repairs`读取。保持loopback Host、精确Origin、严格JSON/大小/时间限制及no-store。接口必须给出可区分的忙碌、配置缺失、版本失配、恢复待处理和未知结果码。

沿用UI-08紧凑工程风：顶部一段操作区，执行中显示简短阶段与停止操作；diff和回归仍在主区。原始ID/hash与预算细账折叠。模型只显示结构化执行事件，不伪造终端stdout或模型思考过程。服务未就绪时指出缺少项并链接环境页。

浏览器在POST前持久化安全pending；存储失败不得启动。丢响应后用相同ID查询状态，仅用GET；用户明确点击“重新提交同一请求”才用同ID幂等POST，并提示此操作可能首次启动执行。刷新不自动重发；未确认接受/未接受时不能清除pending生成新任务。只读GET可有界退避429，写操作不得使用通用自动重试。

## 5. 人工审批与导出

独立 `CandidateDecision` 记录task/candidate、candidate摘要、baseline/tree、oracle/suite、当前comparison摘要、decision、请求ID、时间和revision，不伪装为模型验证结果。接受前重新核对完整证据链、当前版本和diff，陈旧/缺失/未知/有未完执行者拒绝接受。

同request同参幂等；异参冲突。并发接受不同候选必须CAS，禁止“最后写入获胜”；决定变更另记事件和revision。批准后证据失效时显示“历史已接受，当前需重新验证”，不能继续呈现有效通过。下载只返回已核对候选的精确diff字节，文件名由服务端生成；不接收任意路径。

B4的有效接受候选按当前证据判断；失效接受保留历史但不阻塞新的有效接受。receipt 增加任务级 revision 与 `can_*` 权限字段；候选详情 schema2 不被静默改写。

## 6. 必须测试的用例

| 编号 | 情况 | 可观察断言 |
|---|---|---|
| W01 | 首次接收、双击、响应丢失 | 一任务/一claim/一次执行，同参返回相同ID |
| W02 | 同ID异参、墓碑、伪造claim | 409/410或明确拒绝，零新调用 |
| W03 | 两进程争槽、SIGSTOP/SIGKILL | 不越权执行；死owner未知不自动重放 |
| W04 | 接收前缺配置/版本失配 | 零模型零容器；错误可行动 |
| W05 | 首次调用前/模型中/T05/T07停止 | 停止请求与终态区分，预留保留或正确结算，资源精确回收 |
| W06 | 重启/断网/浏览器刷新 | 同任务可回到记录；不自动新建或重复扣预算 |
| W07 | 迁移与旧CLI | 旧表逐行保真；旧案例/恢复/读取契约回归 |
| W08 | 候选审批时版本变化/篡改 | 当前批准被拒，历史记录不改写 |
| W09 | 并发审批与重复提交 | CAS确定结果，一次有效决定，冲突可见 |
| W10 | 下载diff与显示候选 | SHA与原字节一致；错误任务/候选关联被拒 |
| W11 | UI浅深色、390/1440、键盘、错误/未知 | 主操作可发现，无大段无意义ID；具备停止/重试/查看证据入口 |
| W12 | 两案例真实端到端 | 当前网关真实执行，全部尝试保留；验证通过后人工决定与下载，无自动写回 |

测试分层：确定性adapter检验并发/预算/故障；真实Docker检验执行与回收；真实已有模型检验协议与效果；生产构建Playwright验证实际API+SQLite。mock UI通过不能代替真实端到端。每类测试记录命令、样本、跳过和失败，默认pytest跳过项不计已验证。
